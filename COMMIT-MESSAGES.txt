e52fc82
Extract the pricing engine into src/lib/pricing.ts

The config and the arithmetic lived inside PricingCalculator.tsx, so anything
else that needed a price had to re-implement it. The agent portal needs exactly
these numbers, and a second implementation drifts the first time someone edits
one copy and not the other -- a drift that stays invisible until a customer is
holding a PDF that disagrees with the website.

So the module is now the single source of truth: PRICING_CONFIG, the tier
lookup, and computeQuote, plus selectedLines/sanitizeState/withMoney for the
callers that persist and render a quote. PricingCalculator renders what
computeQuote returns and does no arithmetic of its own.

Behaviour is unchanged. Verified by building /he/price before and after: the
rendered markup is identical apart from the build id and chunk hashes.

Tests pin the rules most likely to be broken by a well-meaning edit -- above all
that the tier comparison is strict greater-than, so exactly 1000 earns 20% and
not 25%. An independent oracle re-derives every total by a different route over
500 generated packages.

53a3c99
Add the agent portal: sign in, build a package, send a quote

An agent picks a package from the price list, fills in the customer, and gets a
branded document they can send -- and can see afterwards whether the customer
opened it. Everything is additive: with no Supabase configuration the marketing
site builds and behaves exactly as before, and the login page says so rather
than showing a form that could not work.

Prices come from src/lib/pricing.ts, the same module behind /he/price, so the
two cannot quote different numbers for the same package.

The client never sends money. The browser POSTs which components were selected;
the server looks the prices up and recalc_quote() recomputes the totals in
Postgres. What the agent sees while building is a preview, and the database's
answer is the real one -- so a tampered request can order a different package
but never the same one cheaper.

Visibility is enforced by RLS rather than by query discipline: an agent sees
their own quotes, a manager sees everyone's. A missing WHERE clause in future
code cannot leak one agent's pipeline to another.

The quote document is one HTML template shared by the agent's print view and the
customer's link, so the agent cannot approve one document and the customer
receive a different one. PDFs come from browser printing: Hebrew needs real bidi
shaping, and a browser is the engine most certain to get it right. The route to
a server-rendered PDF is a thin wrapper over the same template if attachments
are ever needed -- see docs/agent-portal.md.

Agents authenticate against Supabase Auth, kept separate from the CRM's users so
the website's login does not depend on the CRM being reachable. Sending is by
link rather than attachment: a link records that the customer opened it, and
lets a corrected quote replace the old one at the same address.

c488d2d
State the portal's table grants explicitly

Supabase's default privileges already cover objects created in public, so this
changes nothing on a normal project. It makes the intent readable next to the
policies, and keeps the migration correct if it is ever replayed somewhere those
defaults are not configured.

The line worth reading is the one that is absent: anon receives no table
privileges at all. The customer link reaches its data only through
quote_by_token(), so a caller holding the anon key gets a permission error on
public.quotes rather than an empty result -- a stricter failure than relying on
row-level filtering alone.

Verified by replaying the migration against a scratch Postgres 16: an agent sees
only their own quotes, a manager sees every quote, an agent cannot insert a
quote under another agent's id or promote themselves to manager, and a draft is
not readable through its customer token until it has been sent.

8f3ef5c
Cut 9.2MB of oversized images and stop the layout shift they caused

about-chef.svg was 7.9MB, and it loads on the homepage in both locales. It is
not really a vector: a 2698x3840 PNG sat inside it as base64, which inflates the
bytes by a third on top of an image already eight times larger than the 460px
box it renders into. Re-encoded to WebP at 1400px tall -- still triple the
pixels a retina display can show -- it is 97KB. The vector markup around it is
byte-identical, and rendering the two side by side at 2x differs by 0.09% mean
per channel, which is nothing.

digital-menus-hero.webp had the same problem in miniature: 1678x2560 and 1.1MB
for a 380px-tall slot. Now 590x900 and 60KB.

Together public/ goes from 12MB to 2.8MB.

The second half is the layout shift. Most of the older <img> tags carry no width
or height, so the browser reserves nothing and the surrounding grid grows when
each image lands. The article components added later already do this correctly;
this brings the rest in line, and marks the below-the-fold ones lazy so they
stop competing with the hero for bandwidth. The carousel needed it most -- it
swaps images in place, so without intrinsic sizes the frame re-laid-out on every
slide change.

Also hoisted ConnectedRestaurant's autoCycle array to module scope. It never
varies, and as a local it was a fresh array each render that the idle-timer
effect then had to pretend not to depend on. lint is now clean; the one
remaining <img> warning is the Meta pixel, which has to stay a raw tag and now
says so.

159ea99
Add team management so agents stop needing SQL to exist

Adding an agent meant opening the Supabase SQL editor. That is fine for the
first one and untenable by the fifth, so there is now a third role that can do
it from inside the product:

  agent    their own quotes
  manager  every agent's quotes
  admin    every agent's quotes, plus the team

An admin adds a colleague, sets a starting password, changes roles, resets a
forgotten one, and deactivates whoever has left. Deactivation takes effect on
that person's next request and keeps their quotes, which is why it is the right
move rather than deletion.

Two things guard the obvious ways to break this. The database refuses to demote
or deactivate the last active admin -- one click away, and unfixable from inside
the product once done. And the API refuses to let an admin deactivate or demote
themselves, which catches the same mistake a step earlier, while there is still
someone around to explain it to.

A password an admin types for someone else is going to be read out over the
phone, so the screen shows it once in the clear with a copy button rather than
pretending otherwise and getting it screenshotted. What actually limits the
exposure is that the account is flagged and requireAgentSession bounces it to
the change-password screen until a new one is chosen -- and every protected page
goes through that function, so no route skips the check.

Creating a login needs the Auth admin API and therefore the service-role key,
which bypasses RLS entirely. The admin check in those two routes is the whole
security boundary, and says so. Auth and public.agents are written together and
the first is unwound if the second fails, so a half-created agent -- a login
that resolves to "signed out", with its address now taken -- cannot happen.

Verified by replaying both migrations on a scratch Postgres and exercising the
roles: an agent cannot promote themselves or anyone else, a manager can read the
roster but not change a role, an admin can do both, the last admin is refused,
and a stepping-down admin is allowed once a second one exists.
