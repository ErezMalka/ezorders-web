Add the agent portal: quote, accept, order

An agent picks a package from the price list, fills in the customer, and sends a
branded quote. The customer reads it at their own link and answers there. A yes
becomes an order, which the portal tracks through installation to go-live.

    quote   draft → sent → viewed → accepted / rejected / expired
    order                   pending_setup → in_setup → live
                                          ↘ cancelled

Everything is additive. With no Supabase configuration the marketing site builds
and behaves exactly as before, and /he/agent/login says so rather than showing a
form that could not work.

One commit rather than the five in COMMIT-MESSAGES.txt: those were made in a
scratch clone whose objects are not in this repository, and every file here is
untracked, so there is no intermediate state to split along that would build.
That file stays as the detailed record of how the first four fifths were built.

WHAT IS HERE

Prices come from src/lib/pricing.ts, the same module behind /he/price, so the
website and the portal cannot quote different numbers for the same package.

The client never sends money. The browser POSTs which components were selected;
the server looks the prices up and recalc_quote() recomputes the totals in
Postgres. A tampered request can order a different package, never the same one
cheaper.

Visibility is row-level security rather than query discipline: an agent sees
their own quotes and orders, a manager sees everyone's. A missing WHERE clause in
future code cannot leak one agent's pipeline to another.

Three roles. agent — their own work. manager — everyone's. admin — everyone's,
plus the team: add a colleague, set a starting password, change a role, reset a
forgotten one, deactivate whoever has left. A database trigger refuses to demote
or deactivate the last active admin, and the API refuses to let an admin do it to
themselves — the same mistake caught a step earlier, while there is still someone
to explain it to.

ORDERS, AND WHAT AN ACCEPTANCE IS

An order is a frozen copy of the quote, not a join to it. A later correction to
the quote cannot change what was sold.

public.quote_responses records who accepted: the name and company id they typed,
when, from which address, with which browser, and the SHA-256 of the exact
document they were looking at. That last field is the one that matters. A drawn
signature proves very little; a hash proves the document has not changed since it
was agreed, which is the claim anyone would actually dispute — recompute it from
the frozen lines and compare. Rejections are recorded the same way, with their
reason, because a no is worth as much to a sales team as a yes.

Most deals still close on the telephone, so an agent can record that from the
quote screen. It is stored as channel='agent' with no signer and no hash, and the
order page says who recorded it rather than implying the customer signed
anything. The alternative — refusing to record it — would mean the orders list
quietly under-counting the business, and a report nobody trusts stops being read.

The customer's page carries no JavaScript at all. This is the moment a sale
closes, on whatever phone they happen to be holding; two ordinary forms and a
<details> element do the whole job, and there is nothing to fail to load.

FOUR THINGS THAT WERE WRONG, FOUND WHILE VERIFYING

Supabase ships `alter default privileges in schema public grant all on tables,
functions, sequences to anon, authenticated, service_role`. Every
`revoke ... from public` written in the earlier migrations was therefore a no-op
on the real project — an explicit grant to anon is not removed by a revoke aimed
at PUBLIC. anon, whose key is in the JavaScript of every page, held full DML on
every portal table and could execute every function. Nothing leaked, because RLS
has no anon policy anywhere, but RLS was carrying the entire load alone, which is
exactly what the schema set out not to depend on. 0004 and 0005 fix it.

Two of those functions mattered. expire_stale_quotes() marks every outstanding
quote past its date as expired; reachable by anon it was a one-request way for
anyone at all to wipe the pipeline. create_order_from_quote() is security definer
with no authorisation of its own by design, and was reachable directly — a lock
with no handle, one leaked uuid from being an open door.

recalc_quote() took the ₪1,950 base setup fee as an argument. It is security
definer and granted to authenticated, and Supabase exposes every such function at
/rest/v1/rpc/, so an agent could POST p_base_setup=0 against their own quote and
reprice it ₪1,950 cheaper with nothing in the audit trail looking unusual. The
fee now lives in pricing_settings, where only the service role can write it, and
the function no longer accepts it. 0007.

expire_stale_quotes() was never scheduled, though 0001's own comment said it must
be. The dashboard's headline figure counts every quote in sent or viewed, so it
climbed and never came down. Now nightly via pg_cron. 0006.

The root cause of the first three is one thing: the scratch Postgres used to
verify the earlier migrations did not have Supabase's default privileges, so it
was more permissive in production than in test — the direction that produces
confident, wrong verification. test/sql/00_supabase_stub.sql now carries those
defaults, and test/sql/20_privileges.sql asserts the resulting matrix, so the
next table or function added to public fails the suite until somebody has decided
who may reach it.

VERIFIED

test/sql/run.sh replays all seven migrations onto a scratch Postgres and runs 54
assertions: the acceptance lifecycle through the same functions the application
calls — accept, reject, expire, double-submit, a draft that must stay invisible,
an agent who must not close a colleague's deal — and the privilege matrix above.

The customer flow was then exercised over HTTP against a PostgREST-shaped shim on
that database: the page renders, accepting creates exactly one order with the
quote's figures frozen onto it, reloading shows the confirmation instead of the
buttons, submitting twice does not sell it twice, the POST does not inflate the
view count, an expired quote refuses a yes and still accepts a no, and the stored
SHA-256 recomputes byte-for-byte from the served document.

29 existing pricing tests, typecheck and lint all pass; next build produces every
route including the two new ones.
